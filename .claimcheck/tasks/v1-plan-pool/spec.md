# Acceptance criteria

Task: failwalk v1, step 4 of the build order in `SPEC.md`: the plan, the bounded pool, and a verdict for every (call site, mode) cell. Base branch for the diff: `v1-inventory-tracer`.
Frozen with `claimcheck spec freeze`. Add nothing after the diff starts.

- [ ] 1. The failure-mode table in `src/tracer/modes.ts` has the rows `timeout`, `dropped`, `500`, `429`, `malformed` and `partial`, each a plain object saying what the injected call does: `timeout` never settles, `dropped` rejects with an error whose `code` is `ECONNRESET`, `500` and `429` reject with a vendor-shaped error carrying that status, `malformed` resolves with `{}`, and `partial` resolves with the first half of an array result (and `{}` for a non-array). `FAILWALK_MODE` accepts every row by name.
- [ ] 2. `failwalk plan --root <path>` reads `failwalk-inventory.json` and `failwalk-trace.json` and writes `failwalk-plan.json`: one entry per (call site, mode) pair with the list of tests that reached that site in the trace. A pair whose site no test reached is written with an empty test list and the verdict `UNREACHED`, and is never run.
- [ ] 3. `failwalk run --root <path> --wrappers <glob> [--concurrency N] [--min-coverage F]` runs the inventory, the trace, and the plan, then one test-runner invocation per planned pair that has tests, filtered to exactly those tests, with `FAILWALK_SITE` and `FAILWALK_MODE` set for that pair. Invocations run through a pool that never has more than N running at once (default 4). Each invocation gets a fresh runner process; nothing is shared between pairs.
- [ ] 4. Every runner invocation is started with a per-test timeout that failwalk sets itself (default 10 seconds, `--test-timeout-ms` to change it), so a `timeout` injection on a call with no timeout of its own ends as `HANG` instead of stalling the run.
- [ ] 5. The verdict for a cell comes from one lookup table over what the invocation did: all planned tests passed → `PASS`; at least one test failed on an assertion → `FAIL`; an unhandled rejection, an uncaught exception, or a runner exit with no test results → `CRASH`; a test ended by the runner's timeout → `HANG`. These four plus `UNREACHED` are the only verdicts this step produces. No `if`/`else` ladder chooses the verdict.
- [ ] 6. `failwalk run` writes `failwalk.json` holding the inventory, the plan, and every cell with its verdict, the tests it ran, and the runner's exit code, and prints a terminal table grouped by wrapper, with `CRASH` and `HANG` cells listed before the rest, each cell naming the site id, the mode, and the verdict.
- [ ] 7. The last line printed is the headline, in this shape: `failwalk: <sites> call sites, <modes> modes, <cells> cells. <covered> covered (<percent>%). <crash> CRASH, <hang> HANG, <fail> FAIL, <unreached> UNREACHED.` `covered` counts `PASS` and `FAIL` cells only.
- [ ] 8. `failwalk run` exits 1 when the covered fraction is below `--min-coverage` (a number from 0 to 1, default 0) and 0 otherwise, including when some cells are `CRASH`.
- [ ] 9. Unit tests cover the mode table, the plan builder (including `UNREACHED` pairs), the verdict lookup for each of the four runtime outcomes, the pool bound, the headline format, and the exit code; `npm test` exits 0.
- [ ] 10. The README gains a "Step 4: the grid" section showing the real terminal table and headline from `failwalk run` against `examples/sample-api`, and the sample app gains at least one call site that produces `HANG` under `timeout` and one that produces `FAIL` under `malformed`, so every verdict except `MOCKED` and `RISK` appears in that output.
- [ ] 11. Nothing in failwalk names, reads or depends on any real-world service or repository, and all new source follows the conventions in `~/.claude/CLAUDE.md`: arrow-function consts, one named-params object per function, lookup tables instead of branch chains, a doc block on every function, no classes, no mutation of inputs, no `await` inside a loop over a collection (the pool is the one place a bounded loop is allowed, and it must be a named helper).
