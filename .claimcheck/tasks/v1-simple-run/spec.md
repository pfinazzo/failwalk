# Acceptance criteria

Task: make failwalk simple to install and run on any repo, and make the README about running it, with the internals folded away. Base branch for the diff: `main`.
Frozen with `claimcheck spec freeze`. Add nothing after the diff starts.

- [ ] 1. `failwalk init [--root <path>] [--wrappers <glob>]` writes `failwalk.config.json` in the root holding `wrappers` (the glob) and `jestConfig` (the override's path). Without `--wrappers` it picks the first folder that exists from one lookup list (`config`, `src/config`, `lib/config`, `clients`, `src/clients`, `services`, `src/services`, `wrappers`, `src/wrappers`), uses `<folder>/**/*.{js,ts}`, and prints which folder it chose and why. When none exists it exits 1 with a message that names `--wrappers`.
- [ ] 2. `failwalk init` also writes `jest.failwalk.config.js` in the root. If the project has `jest.config.js`, `jest.config.cjs` or `jest.config.mjs`, the override loads it and appends failwalk's built setup file to `setupFilesAfterEnv`. If the project's `package.json` has a `jest` field, the override spreads that object and appends the setup file. If neither exists, the override holds only `setupFilesAfterEnv`. The setup file's path is resolved at run time from the installed failwalk package, never hard-coded to a developer's machine.
- [ ] 3. `failwalk init` adds `.failwalk/` and `failwalk-ui.html` to the root's `.gitignore`, creating the file when missing and never adding a line that is already there. It refuses to overwrite an existing `failwalk.config.json` or `jest.failwalk.config.js`, saying which file exists and that `--force` replaces it.
- [ ] 4. `failwalk` with no subcommand, run from a project root that has `failwalk.config.json`, runs the inventory, the trace, the plan and the full grid, writes every output file under `.failwalk/` (the inventory, the trace, the plan, `failwalk.json`), writes `failwalk-ui.html` in the root, prints the headline line, and opens the page unless `--no-open` is given. Without `failwalk.config.json` it exits 1 printing one line that says to run `failwalk init` first. `--wrappers`, `--min-coverage`, `--concurrency` and `--test-timeout-ms` still work as overrides, and the exit code rule from `--min-coverage` is unchanged.
- [ ] 5. The existing subcommands (`inventory`, `trace`, `plan`, `run`, `ui`, `setup-path`) keep working unchanged for anyone who wants the pieces.
- [ ] 6. `package.json` has a `prepare` script that builds `dist`, `files` includes `dist`, and `bin` maps `failwalk` to the built CLI, so `npm install -g github:pfinazzo/failwalk` (with GitHub access to the private repo) and `npx github:pfinazzo/failwalk --version` both work and print the version. `failwalk --version` prints the version from `package.json`.
- [ ] 7. In `examples/sample-api`, `failwalk init` followed by `failwalk --no-open` works from that folder, and the override it writes is equivalent to the one already committed there. The README's "Run it on your repo" section shows exactly that flow, with the sample app as the worked example.
- [ ] 8. The README, from the title to the start of the "How it works" block, is at most 120 lines and contains, in this order: one sentence on what failwalk tells you, the map screenshot from `docs/` with alt text that says what the reader sees, "Install" (the two install commands and the Node requirement), "Run it on your repo" (`failwalk init`, `failwalk`, what files appear), "Read the map" (what green, red, amber and grey mean and what to do about each), and "Use it in CI" (`--no-open`, `--min-coverage`, the exit code). Nothing in that part explains internals, modes, checks, verdict rules or the proof.
- [ ] 9. Everything else now in the README (the step-by-step walkthrough of inventory, trace, injection, the grid, RISK, the proof, the mode and check tables, "What goes wrong in production", limits and development notes) moves, unchanged in substance, under one `<details>` block whose `<summary>` is "How it works" and which is collapsed by default, with each heading demoted one level so the block nests cleanly. No section is deleted.
- [ ] 10. Unit tests cover `init` on temp projects with `jest.config.js`, with a `package.json` `jest` field, and with neither; the wrapper-folder lookup and its exit 1; the refusal to overwrite and `--force`; the `.gitignore` lines added once; and the no-config exit 1 of the bare command. `npm test` exits 0 and the step 7 proof still passes.
- [ ] 11. Nothing in failwalk names, reads or depends on any real-world service or repository, and all new source follows the conventions in `~/.claude/CLAUDE.md`: arrow-function consts, one named-params object per function, lookup tables instead of branch chains, a doc block on every function, no classes, no mutation of inputs, no `await` inside a loop over a collection.
